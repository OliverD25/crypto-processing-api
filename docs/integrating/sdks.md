# Client libraries

Two clients, one server, and one file that stops the three of them disagreeing.
The request layer of each is generated from the committed
[OpenAPI document](../reference/openapi.json) and regenerated by CI, which
fails on any difference — so a route change forces both clients to change in
the same pull request. Around it, about 300 lines per language do the two
things code generation cannot: an `Idempotency-Key` minted per logical call and
reused on every retry of it, and webhook verification over the raw body bytes
in constant time.

Neither package is published yet. Until they are,
[the SDK README](https://github.com/OliverD25/crypto-processing-api/blob/main/sdks/README.md)
lists the two registry accounts that have to exist first, and either client can
be installed from a checkout.

The two sections below are the packages' own READMEs — the text a user reads
on PyPI and npm — included here rather than rewritten, so there is only ever
one copy to correct. Edit them at `sdks/python/README.md` and
`sdks/typescript/README.md`.

## If you are on another stack

There is nothing in either client you cannot do with an HTTP library.
[Integrating](index.md) is the same contract written out by hand: the
lifecycles, the idempotency rule, the five-step webhook handler, and a
signature verifier in Python and Node with no dependencies.

The cases both clients and the server's own verifier are checked against are
published as
[`sdks/signature-vectors.json`](https://github.com/OliverD25/crypto-processing-api/blob/main/sdks/signature-vectors.json).
Assert your verifier against them too. An HMAC scheme with several
implementations drifts in silence, because each one passes its own tests and
the disagreement only shows up as your endpoint rejecting real traffic.
