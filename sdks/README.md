# SDKs

Two clients, one server, and one file that stops the three of them disagreeing.

```
sdks/
  signature-vectors.json     generated  the webhook cases all three assert against
  python/                               PyPI: crypto-processing-client
    crypto_processing_client/
      _generated/            generated  openapi-python-client output
      event_types.py         generated  the 8 webhook payload shapes
      client.py                         idempotency, retries, typed errors
      webhooks.py                       verify_webhook, parse_event
      errors.py
    tests/
  typescript/                           npm: @oliverd25/crypto-processing-client
    src/
      generated/             generated  @hey-api/openapi-ts output
      event-types.ts         generated  the same 8 shapes, in TypeScript
      client.ts                         the same idempotency, retries and errors
      webhooks.ts                       verifyWebhook, parseEvent
      errors.ts
      index.ts
    test/
```

Each package has its own README, which is what a user reads on PyPI or npm:
[`python/README.md`](python/README.md), [`typescript/README.md`](typescript/README.md).

## The shape, and why

**Generated core, thin handwritten layer.** A handwritten client drifts the
moment a route changes and nobody notices until an integrator does. A purely
generated one cannot produce the two things integrators actually need help
with — webhook signature verification and idempotency-key discipline. So the
request layer is generated from
[`docs/reference/openapi.json`](../docs/reference/openapi.json), and about 300
lines per language are written by hand around it.

**Everything marked `generated` above is drift-gated.**
[`.github/workflows/sdk.yml`](../.github/workflows/sdk.yml) regenerates all of
it and fails on any difference, so a route change mechanically forces an SDK
regeneration in the same pull request. Hand-editing a generated file is undone
by the next run; the fix always goes in the spec or in the generator config.

**The two handwritten layers make the same decisions.** Same method names (from
the `operationId`s), same idempotency behaviour, same retry rule, same error
classes under different naming conventions. Where they differ it is because the
language forces it: `verifyWebhook` is async in TypeScript because WebCrypto is
async everywhere.

## Regenerating

```sh
cd "<repo root>"
make sdks
```

That runs, in order: the OpenAPI document and webhook JSON Schema
(`scripts/export_openapi.py`), the signature vectors
(`scripts/export_signature_vectors.py`), the event types for both languages
(`scripts/generate_event_types.py`), then each generator. Running it twice
produces no diff; CI checks that too, because a generator whose output moves
between runs turns the drift gate into a coin toss.

The Python generator is not part of the service's dev dependencies — it is a
build tool, pinned separately:

```sh
cd "<repo root>"; python -m pip install -r sdks/python/requirements-generate.txt; make sdk-python
```

Pinned versions, and why each pin matters:

| Tool | Version | Pinned in |
|---|---|---|
| `openapi-python-client` | 0.29.0 | [`python/requirements-generate.txt`](python/requirements-generate.txt) |
| `ruff` (the generator's post-hook, run `--isolated`) | 0.16.2 | same file |
| `@hey-api/openapi-ts` | 0.99.0 | [`typescript/package.json`](typescript/package.json) + `package-lock.json` |

A different version of any of them writes different code, and the drift gate
would then fail on a machine that happened to resolve a newer one — a red build
with no cause visible in the diff.

## Testing

```sh
cd "<repo root>/sdks/python"; python -m pip install -e ".[dev]"; python -m pytest -q; mypy
cd "<repo root>/sdks/typescript"; npm ci; npm test; npm run typecheck; npm run build
cd "<repo root>"; .venv/Scripts/python -m pytest tests/unit/test_signature_vectors.py -q
```

The third one is the server's half of the signature vectors. All three suites
run the same cases from `signature-vectors.json`, which is the point: an HMAC
scheme with three implementations drifts silently, because each one passes its
own tests and the disagreement only shows up as an integrator's endpoint
rejecting real traffic.

`signature-vectors.json` is generated by the server's own signer and is never
edited by hand. A vector somebody has corrected has stopped being evidence.

## Versions

`client 0.N.x` supports `server 0.N.y`. One repository tag releases the image
and both clients. The full policy is in
[`docs/reference/versioning.md`](../docs/reference/versioning.md).

The two ecosystems spell a pre-release differently — Python `0.2.0.dev0`, npm
`0.2.0-dev.0` — and identically for a final release. A `v*` tag fails CI unless
`python/pyproject.toml` and `typescript/package.json` both carry exactly the
tag's version, because a wrong version on PyPI can never be replaced.

## Turning publishing on

Each publish job stays off until a repository variable says its one-time
registration on the registry is done; until then the job reports what is
missing and passes, so a release does not go red over it. No token is stored
for either registry — both authenticate with the workflow's OIDC identity. The
two setups are independent and can be done in either order.

### 1. PyPI, via trusted publishing

No token is stored anywhere. PyPI verifies the workflow's OIDC identity
instead.

1. Create a PyPI account and sign in.
2. Go to **Your projects → Publishing → Add a new pending publisher**
   (https://pypi.org/manage/account/publishing/) and fill in exactly:

   | Field | Value |
   |---|---|
   | PyPI Project Name | `crypto-processing-client` |
   | Owner | `OliverD25` |
   | Repository name | `crypto-processing-api` |
   | Workflow name | `sdk.yml` |
   | Environment name | `pypi` |

3. In this repository, set the variable that tells the job the registration
   happened — **Settings → Secrets and variables → Actions → Variables → New
   repository variable**, name `PYPI_TRUSTED_PUBLISHER`, value `true`. Or:

   ```sh
   gh variable set PYPI_TRUSTED_PUBLISHER --body true --repo OliverD25/crypto-processing-api
   ```

It is a variable rather than a secret on purpose: there is no secret involved,
it only records that step 2 is done.

### 2. npm, via trusted publishing

No token is stored anywhere here either. npm verifies the workflow's OIDC
identity, and the same identity is what lets the publish step pass
`--provenance` — npm then records which workflow, at which commit, built the
tarball. That works because this repository is public.

**The first publish of the package could not be automated.** Since August 2026
npm treats creating a package as a sensitive operation and requires a human
second factor, so no token and no workflow can do it. `0.2.0` was therefore
published by hand, once, from a maintainer's machine:

```sh
cd "<repo root>/sdks/typescript"; npm ci; npm run build; npm login; npm publish --access public
```

`npm login` opens a browser and asks for the account's second factor, and
`npm publish` asks again. That first version carries no provenance, because
provenance needs the workflow's OIDC identity and there was no workflow. This
step is done and does not come back — it only applies to a package that does
not exist yet.

Now that the package exists, the rest is registration:

1. On npmjs.com, open the package → **Settings → Trusted Publisher → GitHub
   Actions**, and fill in exactly:

   | Field | Value |
   |---|---|
   | Organization or user | `OliverD25` |
   | Repository | `crypto-processing-api` |
   | Workflow filename | `sdk.yml` |
   | Environment | `npm` |

2. In this repository, set the variable that tells the job the registration
   happened:

   ```sh
   gh variable set NPM_TRUSTED_PUBLISHER --body true --repo OliverD25/crypto-processing-api
   ```

The account's **require two-factor authentication for writes** setting can stay
on. It governs token writes, and an OIDC publish is not one.

**Why the token path is gone.** npm's 2026 deprecations end direct publishing
with a stored token around January 2027. A token also stopped being able to
create a package in August 2026 — which is how the first release found out, in
CI, with three one-time-password failures. Trusted publishing is what npm keeps
supporting, and it removes the failure where a token silently expires and takes
the npm half of a release with it.

### What happens then

On the next `v*` tag, each publish job checks whether that exact version is
already on the registry and skips if it is — a release that leaves a client
unchanged ships nothing rather than shipping an identical version. A
pre-release version publishes to npm under the `next` tag so it does not become
what `npm install` gives everyone.

Until both steps are done, tagging is safe: the jobs print what to set up and
succeed.
